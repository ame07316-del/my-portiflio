# اتصال PostgreSQL وإعداد قاعدة البيانات

الموقع يستخدم PostgreSQL في الإنتاج، وPGlite محليًا لو لم يتم ضبط `DATABASE_URL`.
إعداد PostgreSQL وTLS موحّد في `src/lib/postgres-config.mjs` ويُستخدم من التطبيق
ومن `scripts/db.mjs`؛ لا يوجد إعداد SSL منفصل بين المسارين.

> **ما الذي نعرفه عن المزوّد؟** ملفات المشروع وملف `.env.example` يوثّقون Supabase
> وTransaction Pooler، لكن قيمة Vercel السرية غير موجودة في المستودع ولا يمكن
> استنتاج المزوّد الفعلي أو اختبار قاعدة الإنتاج من هذا الكود. افحص اسم المضيف
> داخل لوحة Vercel/لوحة المزوّد بنفسك، ولا ترسل `DATABASE_URL` أو كلمة المرور في
> المحادثة أو screenshots.

---

## 1) الحصول على رابط PostgreSQL الصحيح

1. افتح لوحة قاعدة البيانات الرسمية، واختر المشروع/القاعدة المقصودة.
2. في Supabase: **Connect → Connection string → URI**. انسخ رابط PostgreSQL
   كاملًا من هناك؛ لا تكتبه يدويًا.
3. رابط PostgreSQL يبدأ عادةً بـ `postgresql://` أو `postgres://`. لا تستخدم
   رابط REST/API الذي يبدأ بـ `https://`؛ هذا ليس اتصال PostgreSQL.
4. على Vercel/serverless، استخدم **Transaction Pooler** إذا كان المزوّد يوفّره.
   في Supabase يكون عادةً على المنفذ `6543`. هذا البولر مناسب لاتصالات الدوال
   القصيرة وكثيرة التبدّل. **Session Pooler** أو الاتصال المباشر (عادةً `5432`)
   أنسب غالبًا لسيرفر طويل العمر؛ اتبع تعليمات المزوّد لو كان يوصي بغير ذلك.
5. اترك اسم المستخدم وقاعدة البيانات والمنفذ كما نسخها المزوّد. لو كلمة المرور
   تحتوي رموز URI مثل `@`, `:`, `/` أو `#`، يجب أن تكون URL-encoded؛ إعادة نسخ
   الرابط من لوحة المزوّد تقلل أخطاء الترميز.

شكل توضيحي وهمي فقط — لا تنسخ بيانات هذا المثال:

```text
postgresql://postgres.fakeproject:FAKE_PASSWORD@aws-0-us-east-1.pooler.supabase.com:6543/postgres?sslmode=verify-full
```

## 2) سياسة SSL/TLS في الكود

الإصدار المثبّت والمقفول في `package-lock.json` هو `pg@8.23.0` و
`pg-connection-string@2.14.0`. في `pg`، تمرير `connectionString` مع `ssl` لا يعني
أن كائن `ssl` يفوز: معاملات SSL داخل الرابط تُحلّل بعد دمج الخيارات وقد تستبدل
الكائن الممرّر. لذلك يزيل المحلّل المشترك معاملات SSL من الرابط بعد قراءتها،
ويعطي `pg` إعدادًا محللًا بلا `connectionString`.

مصدر الأولوية: في التطبيق، يقرأ الإعداد `DATABASE_URL` و`DATABASE_SSL_CA` من
بيئة التشغيل التي وفّرها Next/Vercel. في CLI، قيمة shell غير الفارغة لها الأولوية،
ثم `.env.local`، ثم `.env`؛ لا يستبدل ملف `.env` قيمة موجودة. حقول URI الموجودة
(host والمنفذ والقاعدة والمستخدم وكلمة المرور) تتقدم على قيم `PGHOST` و`PGPORT`
وغيرها؛ الحقول المحذوفة فقط قد تستخدم قيم `PG*` الافتراضية. يمرر المحلّل كائن SSL
نهائيًا صريحًا، لذلك لا يستطيع `PGSSLMODE` استبدال سياسة التحقق. يختبر
`test:db-connection` هذا الترتيب وتمرير PEM متعدد الأسطر. بعد قراءة خيارات SSL من
URI، يبني المحلّل كائن `ssl` النهائي الذي يصل إلى `pg`؛ لا يترك `pg` يعيد تحليل
معاملات SSL ويستبدل به التحقق.

السياسة النهائية:

- الاتصال بقاعدة بعيدة يستخدم TLS مع `rejectUnauthorized: true`، مع فحص سلسلة
  الثقة واسم المضيف. لا يوجد fallback إلى اتصال غير موثوق.
- لا يحوّل الكود `verify-full` أو `verify-ca` بصمت إلى وضع أضعف. في نسخة
  `pg-connection-string` الحالية، `require` و`prefer` و`verify-ca` بدون
  `uselibpqcompat=true` تُعامل عمليًا كتحقق كامل؛ المحلّل المشترك يثبت التحقق
  صراحةً حتى لا يتغير الأمان عند تغيّر تفسير المكتبة.
- `sslmode=no-verify` مرفوض، وكذلك `uselibpqcompat=true` مع أوضاع `require` أو
  `prefer` أو `verify-ca` التي قد تعطل تحقق الشهادة/اسم المضيف. لو كان
  `NODE_TLS_REJECT_UNAUTHORIZED=0` موجودًا في بيئة Node، يفشل الاتصال بدلًا من
  تعطيل التحقق. احذف الإعداد القديم؛ لا تستبدله بـ `rejectUnauthorized: false`.
- `sslmode=disable` أو `ssl=0` مسموح فقط لمضيف PostgreSQL محلي مثل `localhost`
  أو `127.0.0.1` أو `::1` (أو Unix socket). تعطيل SSL لمضيف بعيد مرفوض.
- عند عدم كتابة وضع SSL، كل اتصال PostgreSQL يستخدم TLS موثوقًا افتراضيًا، حتى
  المضيف المحلي. اسمح باتصال محلي بلا TLS فقط عند كتابة `sslmode=disable` أو
  `ssl=0` صراحةً؛ يرفض الكود ذلك للمضيف البعيد. وجود `DATABASE_SSL_CA` لا يتجاهل
  إيقاف TLS؛ عند التعارض تظهر رسالة إعداد آمنة.

### لو ظهر خطأ شهادة مثل `self-signed certificate in certificate chain`

إضافة `?sslmode=require` وحدها **لا تثبت الثقة في سلسلة الشهادة** ولا تصلح هذا
الخطأ. لا توقف التحقق، ولا تنسخ شهادة الخادم التي ظهرت أثناء الاتصال الفاشل.

1. راجع صفحة TLS/SSL في لوحة المزوّد أو توثيقه الرسمي، واحصل على **حزمة CA
   موثوقة** التي يوصي بها المزوّد لهذه القاعدة. لا تستخدم شهادة leaf/server فقط،
   ولا مصدرًا عشوائيًا.
2. أضف المتغيّر `DATABASE_SSL_CA` (اختياري) في بيئة Vercel المطلوبة، بقيمة شهادة
   CA أو حزمة شهادات PEM كاملة. يقبل الكود أسطر PEM فعلية أو أسطرًا مكتوبة في
   سطر واحد باستخدام `\n` حرفيًا. القيمة لا تكون مسار ملف ولا مفتاحًا خاصًا.
3. يجب أن يحتوي الرابط على اسم المضيف الذي يطابق الشهادة. لا يوقف `DATABASE_SSL_CA`
   فحص اسم المضيف. عند ضبطه يستخدم Node حزمة CA المحددة لهذه الوصلة بدل مخزن
   الشهادات الافتراضي؛ لذلك ألصق الحزمة الكاملة الموثوقة من المزوّد.
4. إذا كانت القيمة غير صالحة، يعرض التطبيق خطأ إعداد عامًّا وآمنًا من غير طباعة
   الشهادة أو المسار. بعد تعديل المتغيّر احفظه وأعد النشر.

مثال **للتنسيق فقط** وليس شهادة صالحة:

```dotenv
DATABASE_SSL_CA="-----BEGIN CERTIFICATE-----\nBASE64_FROM_PROVIDER\n-----END CERTIFICATE-----"
```

لا تضع شهادة أو كلمة مرور أو `DATABASE_URL` في Git أو المحادثة.

## 3) إضافة المتغيرات في Vercel

من **Vercel → Project → Settings → Environment Variables**:

| الاسم | القيمة |
|---|---|
| `DATABASE_URL` | URI PostgreSQL الذي نسخته من صفحة اتصال المزوّد؛ على Vercel استخدم Transaction Pooler عند توفره |
| `DATABASE_SSL_CA` | اختياري: حزمة CA الموثوقة من المزوّد فقط إذا كانت سلسلة الثقة الافتراضية لا تكفي |
| `DATABASE_POOL_MAX` | `1` إلى `3` مناسب عادةً لدوال serverless |

عند إضافة/تعديل كل متغير:

- اختر النطاق الصحيح: **Production** للدومين المنشور، أو **Preview** لمعاينة الفرع.
  يمكن أن يختلف الرابط بين البيئتين؛ تأكد أن معاينة الفرع تشير للقاعدة المقصودة.
- لو تستخدم تخصيصًا لفرع Preview فتأكد من اختيار اسم الفرع الصحيح أيضًا.
- اضغط **Save** ثم أعد نشر deployment المقصود. متغيرات البيئة لا تتغير داخل
  deployment قديم بمجرد حفظها.
- لا ترسل القيمة السرية لي؛ أدخلها مباشرةً في لوحة الاستضافة أو قناة الأسرار
  المعتمدة لديك.

`DATABASE_URL` فارغ محليًا يعني PGlite داخل `.data/pgdata`. أما على Vercel فهو
إعداد مطلوب؛ نظام الملفات هناك لا يصلح كقاعدة دائمة.

## 4) الفحص من دون تغيير بيانات الإنتاج

`npm run db:check` يستخدم `SELECT version()` وعدّ الصفوف فقط؛ لا ينفّذ schema أو
seed. شغّله محليًا بعد ضبط متغيرات محلية موثوقة إن أردت فحص الاتصال. لا تلصق
الرابط في سجل عام أو محادثة. لو الجداول غير موجودة، سيعرضها `missing` بدل أن
ينشئها.

**لا تستخدم** `npm run db:push` أو `db:import` أو `db:copy-local` كاختبار اتصال؛
هذه أوامر تكتب/تستبدل بيانات. وفتح الموقع نفسه ليس فحصًا read-only: أول تشغيل
على قاعدة جديدة قد ينفذ migrations وseed.

الموقع يهيّئ الجداول والمحتوى المبدئي تلقائيًا عند أول طلب ناجح، داخل transaction
واحدة وعلى نفس اتصال PostgreSQL. يستخدم `pg_advisory_xact_lock` المتوافق مع
Transaction Pooler، مع مهلات للقفل والاستعلام. عند الفشل يحصل rollback ويُغلق
الاتصال قبل إعادة المحاولة. كما يصلح صف `settings` الناقص من غير استبدال إعدادات
موجودة أو إعادة ملء جداول حذف المستخدم محتواها عمدًا.

> قاعدة بيانات جديدة لا تنقل محتوى القاعدة القديمة تلقائيًا. احتفظ بالقديمة، وخذ
> نسخة احتياطية قبل أي نقل مقصود. لا تحذفها ولا تعِد إنشاءها لحل خطأ TLS.

## 5) أوامر قاعدة البيانات

| الأمر | الاستخدام / الأثر |
|---|---|
| `npm run db:check` | استعلامات قراءة لفحص الاتصال وعدّ الصفوف |
| `npm run db:push` | تطبيق schema وقد يعمل seed؛ يكتب في القاعدة |
| `npm run db:export -- backup.json` | تصدير محتوى؛ ينشئ ملفًا محليًا حساسًا |
| `npm run db:import -- backup.json` | استيراد/استبدال محتوى؛ يكتب في القاعدة |
| `npm run db:copy-local` | نسخ بيانات PGlite المحلية إلى `DATABASE_URL`؛ يكتب في القاعدة |
| `npm run db:serve-local` | تشغيل PGlite كسيرفر PostgreSQL محلي |

قاعدة PGlite على القرص تعمل من عملية واحدة فقط. أوقف `npm run dev` قبل تشغيل
أوامر CLI على `.data/pgdata` المحلية.

## 6) اختبارات الإصلاح

كل الاختبارات التالية محلية؛ لا تستخدم قاعدة الإنتاج. اختبار TLS ينشئ CA وشهادة
مؤقتتين عبر OpenSSL داخل مجلد مؤقت، ويثبت قبول CA الموثوقة ورفض سلسلة غير موثوقة
ورفض اسم مضيف غير مطابق. هذا يختبر إعداد TLS والـ handshake المحلي، لكنه **ليس**
اختبارًا لشهادة قاعدة الإنتاج.

```bash
npm run test:db
npm run test:diagnose
npm run test:db-connection
npm run lint
npx tsc --noEmit
npm run build
```
